# App target

The thin SwiftUI shell: menu bar label, popover, Settings, `AppState`, provider registration and notification delivery. It holds views and wiring only; parsing and business logic live in the package ([[decisions/0004-logic-in-contribusagekit-package]]).

## Spec
- **Sections:** SPEC §9.2 (responsibilities), §9.3 (concurrency), §11 (UI), §15.3 and §15.5 (project and entry point), §20 (pitfalls: Settings activation, `MenuBarExtra`, template labels, the notch, notifications, `SMAppService`)
- **Requirements:** FR-4, FR-12, FR-30 to FR-36 (FR-37 dropped, [[decisions/0029-no-first-run-onboarding]]); NFR-3, NFR-8 to NFR-10, NFR-16
- **Tasks:** T-1.1, T-1.7, T-2.7, T-3.2, T-3.5, T-3.6, T-4.6 (UI), T-5.1 to T-5.3, T-5.5, T-5.7, T-5.10, T-5.11, T-5.13 (wiring), T-5.15
- **Path:** `App/` and `Contribusage.xcodeproj`

## Depends on
[[modules/core]], [[modules/claude-code]] and [[modules/github]]. `App/ProviderRegistration.swift` is the only place that lists providers.

## Contract
Built so far (T-1.1): a `MenuBarExtra` with a Quit item. Its label (T-5.10, SPEC §11.1) is `MenuBarItem` in `ContribusageApp.swift`: the symbol and monospaced text of `AppState.menuBarLabel(at:)`, re-read every minute by a `.task` loop that sets a `@State` date, so staleness and resets show without a refresh. A `TimelineView` must not go in a `MenuBarExtra` label: SwiftUI then requests label updates in an endless loop on launch (100 % CPU, memory growing by hundreds of MB per second, no menu bar item), with `.periodic` and `.everyMinute` alike. `AppState.menuBarMode` and `menuBarProvider` are the `menuBarMode` and `menuBarProvider` defaults; `resolvedMenuBarMode` is what shows and `shownMenuBarProvider` the provider it uses (the saved one while on, else the first enabled), shared by the label and the Settings picker; a mode that `usesGitHub` adds GitHub to the menu bar demand (FR-46). Settings' General tab has a Menu bar section: the offered modes, and a provider picker only while more than one provider is registered (FR-12). Build settings per SPEC §15.3: `ARCHS = arm64`, macOS 14.0, warnings as errors, `SWIFT_DEFAULT_ACTOR_ISOLATION = MainActor`, generated Info.plist with `LSUIElement`, hardened runtime, ad-hoc signing. `App/` is a synchronised folder: new files join the target without project file edits ([[decisions/0014-build-and-ci-foundation]]). The popover shell (T-1.7, SPEC §11.2, §11.3): `AppState` holds one `ProviderGroupState` (descriptor plus optional limits and activity `SourceState`) per enabled provider and a GitHub `SourceState`. `Popover/SectionStateView` draws every §11.3 state around a section's content: the first load is the placeholder value `.redacted(reason: .placeholder)`, stale and failed-with-previous values are dimmed (the age sits in every section's `SectionHeader`, so stale needs no extra line), `unparseable` adds "Show raw output". A per-minute `TimelineView` in `PopoverView` sets the `now` environment value that ages and countdowns read. Provider groups are measured; past a cap derived from the screen they move into a `ScrollView` of that height, and only then, since VoiceOver on macOS stops at a scroll area (T-5.7; crossing the cap rebuilds the groups' views and their view state); GitHub and the footer (Refresh ⌘R, Quit ⌘Q) stay pinned. `Popover/AppState+Mock.swift` holds mock data (the GitHub mock and `GitHubSection`'s placeholder are a `ContributionCalendar` plus stats) and one preview per §11.3 row (plus a passed reset), light and dark side by side. Live wiring (T-2.7): `AppState.live()` builds the `ProviderRegistry` from `ProviderRegistration.all(time:)` (the `ClaudeCodeProvider` with `LiveProcessRunner`, `FSEventsFileEvents`, `LiveFileReader`, the login shell from `$SHELL` or `/bin/zsh`, and the `provider.claude-code.pathOverride` default read on every resolution) and the `enabledProviders` default, which it writes back once settled (FR-2); it creates one group per enabled provider in `loading`, then starts the `RefreshCoordinator`, whose updates it applies on the main actor. `SystemConditions` turns `NSWorkspace` sleep and wake, `NWPathMonitor` and `NSProcessInfoPowerStateDidChange` into `ScheduleConditions`, which reach `update(_:)` in order through one `AsyncStream` consumer. `PopoverView.onAppear` reports the popover opening; Refresh and the limits section's Retry call `refreshNow()`; `SectionStateView` takes an optional `retry` closure and shows Retry only with one. `LimitsSection` draws the §11.4 bar (empty after a reset) and the core's window texts (`UsageWindow+Display`, hover: absolute date and time), and one VoiceOver element per window with the §11.7 label; error lines use the §13 wording with the provider's name. Settings (T-3.2, SPEC §11.6): `AppState.live()` builds the one `GitHubAccount` (Keychain service `<bundle id>.github`, FR-16; bundle id and version are force-unwrapped because the build settings always set them); the `Settings` scene whose `TabView` so far holds only `Settings/GitHubTab`: an Account section ("@login" from the `githubLogin` default, "Connected" or, while `AppState.github` is `failed(.unauthorized)`, "Token invalid or expired", and Disconnect → `disconnect`) and one token section (secure field, Connect or Replace → `GitHubAccount.connect`, which writes only after the new token validates, Return submits, a link to GitHub's token page). The tab holds UI state only; the save rule and the Keychain calls live in [[modules/github]]. Error texts come from `SourceError.message(displayName:)` in `SectionStateView.swift`, shared by the popover's `ErrorLine` and Settings (SPEC §13 wording for `unauthorized`). The popover's `SettingsButton` activates the app, then calls `openSettings` (SPEC §20): Connect GitHub without a token, Change token… in place of Retry on a 401's error line (SPEC §13). `ErrorLine` uses small controls and a multicolor warning symbol, and wraps its message to two lines. GitHub wiring (T-3.6): `AppState.live()` builds the one `GitHubAccount` and hands the coordinator a GitHub `Job` (`GitHubReport.policy`, origin `.github`, `report(now:calendar: .current)`), starting GitHub in `loading`; `connectGitHub(token:)` and `disconnectGitHub()` change the token and tell the coordinator in one call. The Settings scene gets `AppState` from the environment, and `GitHubTab` holds UI state only. GitHub's errors show Retry (`refresh()`), except a 401, which shows Change token…. The heatmap (now its own block, T-5.16 below) draws through `WeekColumns`, a `Layout` that puts the days in top-aligned columns of 7 square cells sharing the proposed width and derives its height from that width (26 weeks: 11 pt cells). Hover details (heatmap cells, reset times) are `.help` tooltips; `ContribusageApp.init` registers the `NSInitialToolTipDelay` default of 200 ms, because AppKit's default wait of about 1 s felt like no tooltip at all (SPEC §11.2). Settings window (T-5.2, [[decisions/0028-settings-scope-and-wiring]]): `SettingsView` holds four tabs whose selection is the `settingsTab` default, which `SettingsButton` sets before opening Settings (Locate… → Providers, Connect GitHub and Change token… → GitHub, the footer's ⚙︎ Settings ⌘, → General). General: notification thresholds as a comma-separated field (any numbers stored; the planner applies FR-13's bounds) and `notifyOnReset`. Providers (`ProvidersTab`): one section per registered provider with an enable toggle and its availability from `ProviderRegistry.availability(of:)`; Claude Code adds the located `claude` (path, version, executable type from `ClaudeCodeProvider.located()`), the `pathOverride` (Choose… through `fileImporter`, Clear, Test, which reports whether the override itself runs or another `claude` was used) and the probe interval (5 to 60 min); every section has Delete…, enabled only while the provider is off, with a confirmation dialog, through `JSONStore.deleteProviderData` off the main actor. GitHub adds the refresh interval (10 min to 6 h). Advanced: open the data folder, reset caches (its show insights toggle gave way to the Popover tab in T-5.15). Both intervals are one `IntervalPicker(_:key:policy:choices:)` (in `SettingsView.swift`): minutes in `@AppStorage` whose default is the policy's, and a change calls `intervalsChanged()`. Claude Code's `claude` row is an explicit `Lookup` (searching, not found, found). `NotificationPlanner.Settings.stored` (in `AppState.swift`) is the one reader and writer of the thresholds and `notifyOnReset` keys; the General tab saves only on edits. `AppState` holds a group for every registered provider (registry order) and `enabledIDs`; the popover shows `enabledProviders`. `setEnabled(_:_:)` (FR-2, US-12) updates the registry, then `apply(enabled:)`, the one place the enabled set takes effect (the `enabledProviders` default, `enabledIDs`, starting and cancelling activity consumers; idempotent, so the launch task and an early toggle cannot watch twice), and on enabling calls `coordinator.start()`. A disabled group keeps its last states. Launch at login (T-5.3, FR-34): the General tab's toggle calls `SMAppService.mainApp.register()` or `unregister()` and then shows the status it reads back; a failed call shows its error in red below the toggle (the `GitHubTab` idiom), and nothing is stored (SPEC §10.7). The status is re-read whenever the app becomes active, since approving in System Settings happens outside the app and the open Settings window gets no `onAppear`; while it is `requiresApproval` the toggle stays on and a "Waiting for approval" row offers Open System Settings (`openSystemSettingsLoginItems()`). Nothing offers it on first run: there is no onboarding ([[decisions/0029-no-first-run-onboarding]]). Not in T-5.2: diagnostics (T-5.5, below), menu bar mode and provider (T-5.10, above), bridge instructions (T-6.2). `InsightsSection` (T-6.1, FR-38, [[decisions/0023-structured-insights]]) is a collapsed disclosure group: a segmented picker per period (selected by label, bound to the period shown so a segment is always highlighted), its summary, a `Grid` of shares and the top three of each ranking with right-aligned percents, the tool's note as the title's tooltip and VoiceOver hint. Activity (T-4.6, US-5): `AppState.live()` starts every enabled provider's activity group in `loading` and consumes its `reports()` stream in one task for the app's lifetime (ADR-016); a report with no days at all becomes `notConfigured(.noLocalData)`, any other `loaded` with origin `.activity`. Popover open and every new `lastWake` call `rescan()` on each source (SPEC §12). `ActivitySection` takes the provider's descriptor (its `tokenCategories`, and its display name for VoiceOver): a today row (requests, sessions, total tokens) for the Mac's current day, not the newest day in the report, then the token categories the provider reports in US-5 order (input, output, cache read, cache write), then a Swift Charts bar chart of total tokens for the last 7 calendar days with missing days as 0 and one VoiceOver element: label "<provider> tokens per day, last 7 days", value the highest day, then every day (`Figures.weekSummary`, SPEC §11.7). The mock's days end today so the previews show a today row. Notifications (T-5.1): `AppState.live()` hands the coordinator `Notifications` that read `notificationThresholds` (default 80, 95) and `notifyOnReset` from `UserDefaults` before every plan; the default thresholds live only in `NotificationPlanner.Settings`. `Notifications/NotificationDelivery` (a singleton, since the center holds its delegate weakly) becomes the center's delegate when created, shows banners while the popover makes the app active, asks for permission (alerts only) on the first note and posts each with the note's identifier. The heatmap's keyboard navigation and VoiceOver are T-5.11; its palette came with T-5.7. Diagnostics (T-5.5, FR-36, US-10): the Advanced tab's Copy Diagnostics calls `AppState.copyDiagnostics()`, which puts `diagnostics()` on the general pasteboard: app version and build, macOS version, the chip (`sysctl machdep.cpu.brand_string`), then per registered provider its enabled flag, `SourceState.diagnostics` for limits and activity, skipped lines and the provider's own `diagnostics()` lines, then GitHub's state ([[decisions/0030-provider-diagnostics-hook]]). The GitHub token never reaches `AppState`, so the text cannot hold it. Statistics (FR-42): the footer's Copy button (`doc.on.doc`, tooltip "Copy statistics") calls `copyStatistics()`, whose text (`AppState.statistics(at:)`) follows the popover: per enabled provider a header with the fetch date, each window's label, percent and reset text, the activity today line, token categories and last 7 days, and, while shown, the insights of every period (summary, shares, top three per ranking, not only the period picked in the popover); then GitHub with login and its stats line. A section without values gives its §13 message, a loading or not configured one nothing. Both copied texts and the one pasteboard write live in `AppState+Copy.swift`, apart from the model. The views and the copy share one source per line: `ActivitySection.Figures`, `GitHubReport.statsText`, `Insights.Ranking.shown` (top three) and `ProviderGroupState.insights` (capability and snapshot; the layout gates each caller).

Shared heatmap (T-5.16, FR-48, FR-49, [[decisions/0032-shared-heatmap]]): `Popover/HeatmapBlock.swift` holds the block (header "Heatmap" with the legend, then the grids), `ShownLayer` (a `HeatmapLayer` with its name, hue and dimming), `HeatmapLegend`, `HeatmapGrids` and `WeekColumns`. Combined draws each cell as an `HStack` of stripes, one per layer active that day (one active layer fills the cell, none is the neutral fill), clipped to the rounded cell; Stacked a `WeekColumns` grid per layer, so the columns line up by sharing the width. Every cell's tooltip is the core's FR-49 line. `AppState.heatmap(at:)` (in `HeatmapBlock.swift`) builds the days (`HeatmapLayer.days`, the Mac's calendar) and, in one switch over `heatmapSources` (`layout.heatmapLayers` over the providers with activity), each `ShownLayer` with its data, hue and dimming: GitHub's from its calendar days in range (count and `contributionLevel`), system green, dimmed while stale or failed; a provider's `quartiled` from its activity days' total tokens, with every day from its first reported day on (0 when unreported) and earlier days left out as "no data", in its `heatmapHue`, dimmed while failed (SPEC §11.4). Legend, tooltip and Copy read the layer's `name`. `AppState.blocks` shows the heatmap whenever the core counts it as on; a provider without daily data would count as a layer there (a `ponytail:` note, T-5.17). `GitHubSection` keeps only its stats line. Copy gives "Heatmap, last 26 weeks" and one line per layer with its total. The Popover tab shows the legend and four sample weeks in the chosen style under the picker, hidden from VoiceOver. No month labels (dropped from FR-49). Keyboard and VoiceOver are T-5.11.

Localization and accessibility (T-5.7, NFR-8 to NFR-10, [[decisions/0031-string-catalogs]]): `Resources/Localizable.xcstrings` holds every app string in English and German (the project lists `de` as a known region); literals passed to SwiftUI are extracted as they are, and strings built as `String` (error messages, availability, test results, the activity and GitHub lines, Copy statistics) go through `String(localized:)` where they are built. Plurals (requests, sessions, streak days, contributions) are catalog variations in both languages. Window labels, the billing note, insights, paths and versions are shown as found; diagnostics stay English. Section headers carry the header trait, so VoiceOver can jump between groups. Share percents in the popover and in Copy use the locale's percent style. Provider groups get a `ScrollView` only while they are taller than the cap; otherwise they sit directly in the popover, because VoiceOver on macOS announces a scroll area and goes no further until the user interacts with it. The popover paints no background: the menu bar window's Liquid Glass follows System Settings → Appearance (clear or tinted, the `NSGlassTintAmount` default) and Reduce Transparency. Light mode looks grey over a dark wallpaper with clear glass; the tinted setting changes that. The heatmap's levels 1 to 4 are system green at 40, 60, 80 and 100 % (level 0 `.quaternary`), with 3 pt gaps. The 7 day chart draws narrower rounded bars, today in the accent color and the days before at 45 %. The footer shows icons only (`.labelStyle(.iconOnly)`, titles as tooltips and VoiceOver labels), since the German titles were truncated; the token categories line wraps. Not in T-5.7: the heatmap's keyboard and VoiceOver (T-5.11).

Popover layout wiring (T-5.13, FR-44 to FR-46): `AppState.layout` is the core's `PopoverLayout`, read from and written to the `popoverLayout` default as JSON by `PopoverLayout.stored` (unset or unreadable: the default layout); A change to `layout` (its `didSet`) saves it and applies the demand, so the Popover tab (T-5.15) can bind to it. `apply(enabled:)` now only records the enabled set and calls `applyDemand()`, the one place `PopoverLayout.demand(on:menuBar:)` takes effect: an activity source is watched only while it is in `Demand.activity` (consumers started and cancelled as before, idempotent), and `Demand.github` goes to `coordinator.setGitHubWanted(_:)` through one `AsyncStream` consumer (like the conditions), so quick toggles arrive in order. Until T-5.10 the menu bar counts as using nothing (a `ponytail:` note).

GitHub switch (T-5.14, FR-43): `AppState.gitHubEnabled`, saved under the `githubEnabled` default (unset: on), puts `.github` into the `on` set; its `didSet` applies the demand, so switching off stops the GitHub job through `setGitHubWanted(false)` and keeps the token. The GitHub tab's first row is the switch; while it is off, GitHub leaves the popover and Copy through `AppState.blocks`.

Popover tab and block order (T-5.15, FR-42, FR-44, FR-47, US-13): `AppState.blocks` is `layout.blocks(registered:on:)` over every registered provider and the sources that are on (private `on`; `AppState.isOn(_:)` answers per block), and the heatmap only while it has a layer (T-5.16). `PopoverView` draws these blocks in order, each followed by a divider, all inside the measured, possibly scrolling area; only the footer stays pinned. With no block left it shows "Nothing to show" and "Open Settings…" (`SettingsButton` to the Popover tab). `ProviderGroup` and Copy statistics show `layout.shownSections(of:)` in that order ([[decisions/0034-reorderable-sections]]), and Copy walks the same `blocks`; both resolve a provider block through `AppState.group(_:)`, which traps on an unregistered ID (`providers` holds every registered one). `Settings/PopoverTab` (tab between General and Providers) lists `layout.arranged(registered:)` in a grouped `Form`, one `Section` card per block (header "Blocks" on the first, the drag hint under the last) and one form row per toggle, so the form's row height and separators do the spacing; packing a block's toggles into one row looked cramped. A `RowLabel` style puts every icon in a 20 pt column, and "In heatmap" keeps a hidden `Handle` so its label lines up with the section rows. Block title rows and section rows use one `reorderable(_:among:scope:preview:move:)` modifier (in `PopoverTab.swift`), generic over a `RawRepresentable<String>` item (`BlockID`, `SectionKind`); it owns the payload "<scope>/<raw value>" and the lookup, so callers only say how to move: a handle (`line.3.horizontal`), `.draggable` with the row's label on a material card as the drag preview, `.dropDestination` whose target row lights up in the tint, and the move inside `withAnimation(.snappy)` so rows slide; Reduce Motion drops both animations. Blocks use the scope `block` and `layout.move(_:to:registered:)`; sections use their provider's ID as the scope, so they move only within their group, and `layout.move(_:to:of:)`. The dragged row takes the target's place. Each block takes its label, off note and capabilities from one `switch`; "In heatmap" shows for a source with daily data (GitHub, or a provider with the activity capability): a visibility toggle, "In heatmap" with the activity capability, and a toggle per section in `layout.sections(of:)` whose `capability` the provider declares, bound to `layout[shows:of:]` and labelled with a symbol; a block whose source is off (`layout.isOn`) is drawn secondary with a note pointing to Providers or the GitHub tab. The heatmap style picker (Combined, Stacked) has the three-layer hint; its legend preview came with T-5.16. Block and heatmap toggles bind through `Binding.excludes(_:)`, since the layout stores what is hidden or left out. Block drag was checked by hand in the built app; section drag and the animations still need that check.

Tool texts ([[decisions/0033-provider-tool-texts]]): `LimitsSection` takes the provider's descriptor and shows `descriptor.toolText(window.label)` in the row and its VoiceOver label; `InsightsSection` takes the descriptor too, whose `toolText` serves the period picker, the summary and the note (tooltip and VoiceOver hint); Copy statistics do the same. The printed texts stay the `ForEach` ids and the picked period.

## Things that bite
- `ForEach.onMove` reorders only inside a `List`; in a grouped `Form` on macOS rows cannot be dragged at all (the first Popover tab shipped that way). Rows use `.draggable` and `.dropDestination` instead.
- An app localized only in English runs as `en_<region>`: a German Mac gets German number and time conventions but English weekdays and units. German words in dates need the German localization, not a different `Locale`.
- After a localization is added, an incremental build can keep a stale copy of the package's resource bundle inside the app (no `de.lproj`); delete the built `.app` and build again.
- `xcodebuild` extracts strings into `.stringsdata` but never writes them into a catalog; only the Xcode IDE syncs on build. After a command line build, `xcrun xcstringstool sync <catalog> --stringsdata <files>` does it (the CI step lists the files), and the synced copy must keep the name `Localizable.xcstrings`, because sync matches the table by file name: a copy named otherwise loses every key.
- Foundation's pseudo-localization flags (`-NSDoubleLocalizedStrings`, `-NSAccentuateLocalizedStrings`) also rewrite plural format strings, so a plain `String(format:)` lookup prints `%#@…@` fragments; that is the flag, not the catalog.
- `ImageRenderer` draws AppKit-backed controls (`ProgressView`, borderless buttons) as placeholders, so the limits bar is a drawn `Capsule`; that also keeps the §11.4 colours exact.
- A heatmap wider than the popover widens the `MenuBarExtra` window and clips both sides: the first live calendar (365 days, 53 columns, ~636 pt) did that. The mock and placeholder had used 182 days, which hid the width; they are now 26 full weeks. Fixed 10 pt cells then left 26 pt empty on the right. Cells sized by `aspectRatio(1, contentMode: .fit)` shrank to dots in the real window: the `MenuBarExtra` window proposes too little height, and a fit ratio takes the smaller side (`ImageRenderer` proposes unlimited height and hid it; a hosting controller asked for 360 × 0 reproduces it). Size nothing in the popover from the proposed height.
- Return in a focused `SecureField` or `TextField` fires only its `onSubmit`, never the `.keyboardShortcut(.defaultAction)` button; the default button gets Return only while no field has focus (checked with synthetic key events in a hosting view). A form that submits on Return needs both, and the submit function guards against an empty field itself.
- `xcodebuild` needs a full Xcode selected; the Command Line Tools build the package but not the app.
- Notifications (T-5.1) and the Settings window (T-5.2) were checked by hand in the built `.app` copied to `/Applications`: the ad-hoc signed Debug build with its stable bundle id gets the permission prompt and delivers banners; Xcode's Run button is not a valid test (SPEC §20). A note whose permission prompt is denied is lost for its cycle, since the keys are persisted before delivery (FR-15); to test again, quit and remove `notificationKeys` from `state.json`.
- `MenuBarExtra` has no "is open" signal (SPEC §20); the popover-open trigger relies on `onAppear` of the window content firing on every open, which still needs a manual check (no automated way to click the menu bar item here).
- In the `MenuBarExtra` window a `ScrollView` has no height of its own: a `ViewThatFits` over groups and a scroll view fell back to the scroll view and drew the groups at zero height once they arrived asynchronously (the mock data had hidden it). Hence the measured height.
- Foundation's duration formatting rounds under 30 s to "0 min", hence the 1 min floor in the reset text; en_US abbreviates hours as "hr", not SPEC's "h".
- SPEC §15.5 registers a `DebugFakeProvider` under `CONTRIBUSAGE_FAKE_PROVIDER`, but `FakeProvider` lives in `ContribusageTestSupport`, which is not a product and never links into the app. Decide in T-5.12 where the debug provider lives.
