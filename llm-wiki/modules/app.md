# App target

The thin SwiftUI shell: menu bar label, popover, Settings, `AppState`, provider registration and notification delivery. It holds views and wiring only; parsing and business logic live in the package ([[decisions/0004-logic-in-contribusagekit-package]]).

## Spec
- **Sections:** SPEC §9.2 (responsibilities), §9.3 (concurrency), §11 (UI), §15.3 and §15.5 (project and entry point), §20 (pitfalls: Settings activation, `MenuBarExtra`, template labels, the notch, notifications, `SMAppService`)
- **Requirements:** FR-4, FR-12, FR-30 to FR-36 (FR-37 dropped, [[decisions/0029-no-first-run-onboarding]]); NFR-3, NFR-8 to NFR-10, NFR-16
- **Tasks:** T-1.1, T-1.7, T-2.7, T-3.2, T-3.5, T-3.6, T-4.6 (UI), T-5.1 to T-5.3, T-5.5, T-5.7, T-5.10, T-5.11
- **Path:** `App/` and `Contribusage.xcodeproj`

## Depends on
[[modules/core]], [[modules/claude-code]] and [[modules/github]]. `App/ProviderRegistration.swift` is the only place that lists providers.

## Contract
Built so far (T-1.1): a `MenuBarExtra` with a Quit item. Build settings per SPEC §15.3: `ARCHS = arm64`, macOS 14.0, warnings as errors, `SWIFT_DEFAULT_ACTOR_ISOLATION = MainActor`, generated Info.plist with `LSUIElement`, hardened runtime, ad-hoc signing. `App/` is a synchronised folder: new files join the target without project file edits ([[decisions/0014-build-and-ci-foundation]]). The popover shell (T-1.7, SPEC §11.2, §11.3): `AppState` holds one `ProviderGroupState` (descriptor plus optional limits and activity `SourceState`) per enabled provider and a GitHub `SourceState`. `Popover/SectionStateView` draws every §11.3 state around a section's content: the first load is the placeholder value `.redacted(reason: .placeholder)`, stale and failed-with-previous values are dimmed (the age sits in every section's `SectionHeader`, so stale needs no extra line), `unparseable` adds "Show raw output". A per-minute `TimelineView` in `PopoverView` sets the `now` environment value that ages and countdowns read. Provider groups sit in a `ScrollView` whose height is the groups' measured height, capped by the screen; GitHub and the footer (Refresh ⌘R, Quit ⌘Q) stay pinned. `Popover/AppState+Mock.swift` holds mock data (the GitHub mock and `GitHubSection`'s placeholder are a `ContributionCalendar` plus stats) and one preview per §11.3 row (plus a passed reset), light and dark side by side. Live wiring (T-2.7): `AppState.live()` builds the `ProviderRegistry` from `ProviderRegistration.all(time:)` (the `ClaudeCodeProvider` with `LiveProcessRunner`, `FSEventsFileEvents`, `LiveFileReader`, the login shell from `$SHELL` or `/bin/zsh`, and the `provider.claude-code.pathOverride` default read on every resolution) and the `enabledProviders` default, which it writes back once settled (FR-2); it creates one group per enabled provider in `loading`, then starts the `RefreshCoordinator`, whose updates it applies on the main actor. `SystemConditions` turns `NSWorkspace` sleep and wake, `NWPathMonitor` and `NSProcessInfoPowerStateDidChange` into `ScheduleConditions`, which reach `update(_:)` in order through one `AsyncStream` consumer. `PopoverView.onAppear` reports the popover opening; Refresh and the limits section's Retry call `refreshNow()`; `SectionStateView` takes an optional `retry` closure and shows Retry only with one. `LimitsSection` draws the §11.4 bar (empty after a reset) and the core's window texts (`UsageWindow+Display`, hover: absolute date and time), and one VoiceOver element per window with the §11.7 label; error lines use the §13 wording with the provider's name. Settings (T-3.2, SPEC §11.6): `AppState.live()` builds the one `GitHubAccount` (Keychain service `<bundle id>.github`, FR-16; bundle id and version are force-unwrapped because the build settings always set them); the `Settings` scene whose `TabView` so far holds only `Settings/GitHubTab`: an Account section ("@login" from the `githubLogin` default, "Connected" or, while `AppState.github` is `failed(.unauthorized)`, "Token invalid or expired", and Disconnect → `disconnect`) and one token section (secure field, Connect or Replace → `GitHubAccount.connect`, which writes only after the new token validates, Return submits, a link to GitHub's token page). The tab holds UI state only; the save rule and the Keychain calls live in [[modules/github]]. Error texts come from `SourceError.message(displayName:)` in `SectionStateView.swift`, shared by the popover's `ErrorLine` and Settings (SPEC §13 wording for `unauthorized`). The popover's `SettingsButton` activates the app, then calls `openSettings` (SPEC §20): Connect GitHub without a token, Change token… in place of Retry on a 401's error line (SPEC §13). `ErrorLine` uses small controls and a multicolor warning symbol, and wraps its message to two lines. GitHub wiring (T-3.6): `AppState.live()` builds the one `GitHubAccount` and hands the coordinator a GitHub `Job` (`GitHubReport.policy`, origin `.github`, `report(now:calendar: .current)`), starting GitHub in `loading`; `connectGitHub(token:)` and `disconnectGitHub()` change the token and tell the coordinator in one call. The Settings scene gets `AppState` from the environment, and `GitHubTab` holds UI state only. GitHub's errors show Retry (`refresh()`), except a 401, which shows Change token…. The popover heatmap draws `calendar.weeks.suffix(26)` (FR-20: fixed range, no setting) through `WeekColumns`, a `Layout` that puts the days in top-aligned columns of 7 square cells sharing the proposed width and derives its height from that width (26 weeks: 11 pt cells). Hover details (heatmap cells, reset times) are `.help` tooltips; `ContribusageApp.init` registers the `NSInitialToolTipDelay` default of 200 ms, because AppKit's default wait of about 1 s felt like no tooltip at all (SPEC §11.2). Settings window (T-5.2, [[decisions/0028-settings-scope-and-wiring]]): `SettingsView` holds four tabs whose selection is the `settingsTab` default, which `SettingsButton` sets before opening Settings (Locate… → Providers, Connect GitHub and Change token… → GitHub, the footer's ⚙︎ Settings ⌘, → General). General: notification thresholds as a comma-separated field (any numbers stored; the planner applies FR-13's bounds) and `notifyOnReset`. Providers (`ProvidersTab`): one section per registered provider with an enable toggle and its availability from `ProviderRegistry.availability(of:)`; Claude Code adds the located `claude` (path, version, executable type from `ClaudeCodeProvider.located()`), the `pathOverride` (Choose… through `fileImporter`, Clear, Test, which reports whether the override itself runs or another `claude` was used) and the probe interval (5 to 60 min); every section has Delete…, enabled only while the provider is off, with a confirmation dialog, through `JSONStore.deleteProviderData` off the main actor. GitHub adds the refresh interval (10 min to 6 h). Advanced: show insights (`showInsights`, read by `ProviderGroup` and Copy), open the data folder, reset caches. Both intervals are one `IntervalPicker(_:key:policy:choices:)` (in `SettingsView.swift`): minutes in `@AppStorage` whose default is the policy's, and a change calls `intervalsChanged()`. Claude Code's `claude` row is an explicit `Lookup` (searching, not found, found). `NotificationPlanner.Settings.stored` (in `AppState.swift`) is the one reader and writer of the thresholds and `notifyOnReset` keys; the General tab saves only on edits. `AppState` holds a group for every registered provider (registry order) and `enabledIDs`; the popover shows `enabledProviders`. `setEnabled(_:_:)` (FR-2, US-12) updates the registry, then `apply(enabled:)`, the one place the enabled set takes effect (the `enabledProviders` default, `enabledIDs`, starting and cancelling activity consumers; idempotent, so the launch task and an early toggle cannot watch twice), and on enabling calls `coordinator.start()`. A disabled group keeps its last states. Launch at login (T-5.3, FR-34): the General tab's toggle calls `SMAppService.mainApp.register()` or `unregister()` and then shows the status it reads back; a failed call shows its error in red below the toggle (the `GitHubTab` idiom), and nothing is stored (SPEC §10.7). The status is re-read whenever the app becomes active, since approving in System Settings happens outside the app and the open Settings window gets no `onAppear`; while it is `requiresApproval` the toggle stays on and a "Waiting for approval" row offers Open System Settings (`openSystemSettingsLoginItems()`). Nothing offers it on first run: there is no onboarding ([[decisions/0029-no-first-run-onboarding]]). Not in T-5.2: diagnostics (T-5.5, below), menu bar mode and provider (T-5.10), bridge instructions (T-6.2). `InsightsSection` (T-6.1, FR-38, [[decisions/0023-structured-insights]]) is a collapsed disclosure group: a segmented picker per period (selected by label, bound to the period shown so a segment is always highlighted), its summary, a `Grid` of shares and the top three of each ranking with right-aligned percents, the tool's note as the title's tooltip and VoiceOver hint. Activity (T-4.6, US-5): `AppState.live()` starts every enabled provider's activity group in `loading` and consumes its `reports()` stream in one task for the app's lifetime (ADR-016); a report with no days at all becomes `notConfigured(.noLocalData)`, any other `loaded` with origin `.activity`. Popover open and every new `lastWake` call `rescan()` on each source (SPEC §12). `ActivitySection` takes the descriptor's `tokenCategories`: a today row (requests, sessions, total tokens) for the Mac's current day, not the newest day in the report, then the token categories the provider reports in US-5 order (input, output, cache read, cache write), then a Swift Charts bar chart of total tokens for the last 7 calendar days with missing days as 0 and one VoiceOver element listing each weekday's total. The mock's days end today so the previews show a today row. Notifications (T-5.1): `AppState.live()` hands the coordinator `Notifications` that read `notificationThresholds` (default 80, 95) and `notifyOnReset` from `UserDefaults` before every plan; the default thresholds live only in `NotificationPlanner.Settings`. `Notifications/NotificationDelivery` (a singleton, since the center holds its delegate weakly) becomes the center's delegate when created, shows banners while the popover makes the app active, asks for permission (alerts only) on the first note and posts each with the note's identifier. The heatmap's palette, keyboard navigation and VoiceOver are T-5.11. Diagnostics (T-5.5, FR-36, US-10): the Advanced tab's Copy Diagnostics calls `AppState.copyDiagnostics()`, which puts `diagnostics()` on the general pasteboard: app version and build, macOS version, the chip (`sysctl machdep.cpu.brand_string`), then per registered provider its enabled flag, `SourceState.diagnostics` for limits and activity, skipped lines and the provider's own `diagnostics()` lines, then GitHub's state ([[decisions/0030-provider-diagnostics-hook]]). The GitHub token never reaches `AppState`, so the text cannot hold it. Statistics (FR-42): the footer's Copy button (`doc.on.doc`, tooltip "Copy statistics") calls `copyStatistics()`, whose text (`AppState.statistics(at:)`) follows the popover: per enabled provider a header with the fetch date, each window's label, percent and reset text, the activity today line, token categories and last 7 days, and, while `showInsights` is on, the insights of every period (summary, shares, top three per ranking, not only the period picked in the popover); then GitHub with login and its stats line. A section without values gives its §13 message, a loading or not configured one nothing. Both copied texts and the one pasteboard write live in `AppState+Copy.swift`, apart from the model. The views and the copy share one source per line: `ActivitySection.Figures`, `GitHubReport.statsText`, `Insights.Ranking.shown` (top three) and `ProviderGroupState.insights` (capability and snapshot; the `showInsights` setting gates each caller).

## Things that bite
- `ImageRenderer` draws AppKit-backed controls (`ProgressView`, borderless buttons) as placeholders, so the limits bar is a drawn `Capsule`; that also keeps the §11.4 colours exact.
- A heatmap wider than the popover widens the `MenuBarExtra` window and clips both sides: the first live calendar (365 days, 53 columns, ~636 pt) did that. The mock and placeholder had used 182 days, which hid the width; they are now 26 full weeks. Fixed 10 pt cells then left 26 pt empty on the right. Cells sized by `aspectRatio(1, contentMode: .fit)` shrank to dots in the real window: the `MenuBarExtra` window proposes too little height, and a fit ratio takes the smaller side (`ImageRenderer` proposes unlimited height and hid it; a hosting controller asked for 360 × 0 reproduces it). Size nothing in the popover from the proposed height.
- Return in a focused `SecureField` or `TextField` fires only its `onSubmit`, never the `.keyboardShortcut(.defaultAction)` button; the default button gets Return only while no field has focus (checked with synthetic key events in a hosting view). A form that submits on Return needs both, and the submit function guards against an empty field itself.
- `xcodebuild` needs a full Xcode selected; the Command Line Tools build the package but not the app.
- Notifications (T-5.1) and the Settings window (T-5.2) were checked by hand in the built `.app` copied to `/Applications`: the ad-hoc signed Debug build with its stable bundle id gets the permission prompt and delivers banners; Xcode's Run button is not a valid test (SPEC §20). A note whose permission prompt is denied is lost for its cycle, since the keys are persisted before delivery (FR-15); to test again, quit and remove `notificationKeys` from `state.json`.
- `MenuBarExtra` has no "is open" signal (SPEC §20); the popover-open trigger relies on `onAppear` of the window content firing on every open, which still needs a manual check (no automated way to click the menu bar item here).
- In the `MenuBarExtra` window a `ScrollView` has no height of its own: a `ViewThatFits` over groups and a scroll view fell back to the scroll view and drew the groups at zero height once they arrived asynchronously (the mock data had hidden it). Hence the measured height.
- Foundation's duration formatting rounds under 30 s to "0 min", hence the 1 min floor in the reset text; en_US abbreviates hours as "hr", not SPEC's "h".
- SPEC §15.5 registers a `DebugFakeProvider` under `CONTRIBUSAGE_FAKE_PROVIDER`, but `FakeProvider` lives in `ContribusageTestSupport`, which is not a product and never links into the app. Decide in T-5.9 where the debug provider lives.
